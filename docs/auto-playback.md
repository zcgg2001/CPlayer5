# 自动音源与最高可用音质

2026-11-08 在生产域名 `https://music.505zc.tech` 做了 12 个音源的样本测试，并复测 Meting、ChKSz、GD。

## 测试结果

每轮搜索「晴天」「青花瓷」「稻香」，使用首个结果，解析该渠道最高档，再读取真实音频的前 4 KiB。最多两个音源同时测试，同一音源顺序执行；遇到认证、额度或限流拒绝立即停止该音源。时延是搜索、解析、片段读取的总和，包含缓存与本地网络影响。

| --- | --- | --- |
| chksz | 6 / 6 | 2803 ms |
| gequke | 3 / 3 | 2626 ms |
| jianbin-kugou | 3 / 3 | 3477 ms |

在这组样本中，ChKSz 的成功率和速度较好；Meting 也全部成功，并在「晴天」「青花瓷」返回了 FLAC。「稻香」返回 MP3。GD 两轮均有一个搜索样本返回 503；Bilibili 首次请求即返回 429，停止后续测试。多数其他渠道返回 MP3。

进一步读取同一歌曲 ID `259138` 的 FLAC STREAMINFO 文件头，ChKSz 为 24-bit / 192 kHz，Meting 和 GD 为 16-bit / 44.1 kHz。ChKSz 与 GD 的 HTTP Content-Type 虽为 audio/mpeg，实际文件头是 fLaC，不能仅凭 MIME 判断音质。因此默认优先使用 ChKSz，Meting 作为第一后备。

接口自报的「母带 / Hi-Res」不证明文件确有该质量。新播放器会把明确为 MP3 的地址按有损音频显示，不能仅凭请求档位标为无损。原始样本见 [JSON 记录](music-source-probes-2026-11-08.json)。这不是长期稳定性或十用户并发测试。

## 播放策略

- 搜索结果点击播放时，优先使用搜索当时选中的渠道；歌曲资料中手选的渠道也同样优先。选择随歌曲保留在队列中，不因后来切换搜索筛选而改变。每个渠道从最高支持档位开始，只有不可播放或已处于失败冷却时才用其他渠道。
- 没有手选渠道的推荐、聚合搜索或旧歌单继续自动选源：ChKSz 初始优先，Meting、GD 及其他渠道作为后备；浏览器随后根据真实播放成功、失败次数与启动耗时调整顺序。
- 使用已知的同平台歌曲 ID 直接换渠道；跨平台或不通用的 ID 必须重新搜索，并符合曲名、艺人、版本、专辑和时长匹配规则。不同演唱者、Live、Remix、伴奏不会仅凭名字替换。Bilibili 视频保留自身内容身份。
- 资源为空、音质不可用或浏览器不支持编码时降一档；认证、配额、限流或网络超时直接转向其他渠道。成功解析 URL 后，必须实际启动媒体才记为播放成功。
- 搜索候选最多等待 8 秒，单次解析最多 12 秒，高音质音频启动最多等待 15 秒，播放后的连续停滞检测为 8 秒。明确错误立即推进下一候选，网络无响应需要等待超时判断。恢复时尽量保留时间位置；音频必须支持跳转。
- 每次播放最多 16 次解析、5 次跨渠道搜索，解析、搜索与失败音频等待累计最多 60 秒；没有后台无限轮询。全部候选失败会显示重试和手动选择音源入口。
- 失败渠道冷却 30 秒至 5 分钟，限流至少 5 分钟并尊重 Retry-After，认证或额度错误冷却 15 分钟。健康记录只保存在当前浏览器，有效期 24 小时；不代表站点级集中限流。
- 自动模式关闭额外的下一首预解析，减少无效请求。手动音质选择作用于当前歌曲，下一首重新从最高档开始。搜索选中的渠道优先于全局排名和启动耗时评分；仍遵守限流与认证拒绝的冷却。
- 用户暂停和浏览器禁止自动播放都不会被误判为音源失败。歌词和封面延迟返回不能覆盖恢复后的当前歌曲。

## 验证与部署

自动化回归涵盖音质递降、429 冷却、跨平台匹配、取消旧请求、音频解码失败、网络中断、卡顿、保留进度以及自动播放权限。真实浏览器使用受控接口和可解码 WAV 测试完整手机交互与桌面布局。

Service Worker 升级至 v74，包含此前 v1.4.0 的移动入口、播放提示和推荐加载优化。

部署版本：`4cf93df5-1f0e-46fe-a556-2e77bd2d1db3`。正式域名的 Service Worker、路由、播放控制和提示模块均与本地文件逐字一致。104 项 Python、328 项 JavaScript、8 项 Workers 测试通过；构建、部署预检查与服务冒烟通过。

线上浏览器使用真实歌曲 ID `259138` 验证首播与模拟断线恢复：ChKSz 母带档实际开始播放，随后自动转向 Meting 无损，并保持至少 12 秒的进度。较短的 6.5 秒解析超时在冷请求中曾导致恢复失败，成功复测后再次出现相同问题，因此已把单次解析预算调整至 12 秒、高音质音频启动调整至 15 秒，并将累计失败尝试限制为 60 秒；修复恢复进度被重复设置导致二次跳转的问题；这说明自动策略仍受上游瞬时可用性影响，不能承诺零中断。测试使用独立的内存偏好和静音音频，不改变用户歌单。

最终部署后的真实浏览器验证通过：ChKSz → 模拟网络中断 → Meting，恢复后实际播放推进至 12.503892 秒，未出现最终播放错误。
